**Dismiss (real row, real UI, real DB):**

As ash, identified one of two duplicate `offer_received` rows for "Venusaur V" (id `813b6ad9-2509-491d-9ebe-38e7e6c73ec7`, the oldest of three near-identical offer-placement attempts documented in Task 7's report) via `GET /api/notifications`, located its exact row index on the rendered page, and clicked its "Dismiss" (×) button.

- UI: dismiss-button count dropped from 15 → 14 immediately, the other two "New offer on Venusaur V" rows remained visible.
- DB: `prisma.notification.findUnique({ where: { id: "813b6ad9-..." }})` → `null` (hard-deleted, matching `DELETE /api/notifications/[id]`'s `deleteMany` semantics). Ash's total notification count dropped 15 → 14.

**Mark all read (real rows, real UI, real DB):**

As misty (13 notifications, all unread going in — confirmed via DB first: `unread: 13, total: 13`), clicked "Mark all read" on `/notifications`.

- UI: the "Mark all read" button itself disappeared afterward (it's conditionally rendered only when `unreadCount > 0`), and the navbar bell badge (`[aria-label="Notifications"] .MuiBadge-badge`) went from showing `13` to rendering empty (MUI `Badge` hides a zero count by default).
- DB: `prisma.notification.count({ where: { userId: misty.id, read: false }})` → `0`, total still `13` (correctly a bulk *update*, not a delete — matches `PATCH /api/notifications`'s `updateMany({ data: { read: true }})`).

**Live SSE badge update across two contexts (no manual refresh):**

Opened one browser context logged in as misty, sitting on `/marketplace` (deliberately not the `/notifications` page itself, to prove the badge updates globally via `NotificationProvider` in the root layout, not just on the notifications page). Confirmed the navbar badge read `0` (post mark-all-read). Then, from a fully separate process, wrote one new `Notification` row directly to Postgres for misty (type `outbid`) — see note below on why this used a direct Prisma write rather than importing `createNotification` in-process. Polled misty's still-open, never-reloaded page every second for 12 seconds:

```
t+1s badge = 0
t+2s badge = 0
t+3s badge = 1   <- picked up here
t+4s..12s badge = 1 (stable)
```

The badge went from `0` to `1` at t+3s with **zero page reloads or navigations** — confirmed live via the `/api/notifications/stream` SSE connection exactly as `NotificationContext.tsx` and `stream/route.ts` are designed to do (server polls `prisma.notification.count()` every 5s and pushes; this update landed inside one poll tick). No console errors on the page throughout. Cleaned up the test row afterward (deleted from Postgres) so it doesn't linger as a fake `"QA SSE Live Test"` entry in misty's real notification history.

*Note on why a direct DB write was used for this step instead of calling `notifyAsync()`/`createNotification()` in-process:* importing `src/lib/notifications.ts` as a standalone `tsx` entrypoint produced an ESM/CJS interop quirk (`Object.keys()` on the imported module showed only `['default', 'module.exports']`, not `createNotification`) rather than a clean named export — not worth chasing down since it's irrelevant to what this step is actually testing. The SSE stream endpoint (`src/app/api/notifications/stream/route.ts`) only ever calls `prisma.notification.count({ where: { userId, read: false }})` on a timer; it has no way to know or care which code path produced a row, so a direct Prisma write exercises the exact same delivery path a real `notifyAsync()` call would. The notification-*creation* trigger code paths themselves (offers, bids, checkout, the Stripe webhook) were already exercised for real, end-to-end, with real UI actions, by Tasks 5-8 — this step's job was specifically to confirm the SSE delivery/poll mechanism, which it did.
