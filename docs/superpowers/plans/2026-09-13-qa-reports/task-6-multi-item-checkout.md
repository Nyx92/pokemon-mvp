# Task 6: Multi-item cart checkout

Fixtures: buyer = ash (`ash@pokemon.com`), seller = misty (`misty@pokemon.com`), card names = "Starmie GX" + "Gyarados VMAX".

## Tested

Drove a real browser (playwright-core + cached Chromium, per Shared Setup) logged in as ash, added one misty-owned "Starmie GX" listing (`649ef08c-e1ca-45e2-8b0e-6afad6390074`, $28.00) and one misty-owned "Gyarados VMAX" listing (`ce14ae68-9ec4-4ffd-bed1-b6afefae3ef0`, $35.00) to the cart in the same session, and completed checkout once with a single real Stripe test-mode payment (card `4242 4242 4242 4242`).

- Cart correctly showed both items selected with a summed subtotal of $63.00 before checkout (confirmed via the cart page UI and via `GET /api/cart`).
- Checkout produced **one** Stripe Checkout Session (`cs_test_b167WA9kqiBo1GFPweiCNlKaQNePL1lP2g9anyPf2ljbHZ5VRoG4EaNBVh`) covering both items, and the buyer was redirected to `/purchases?success=1&session_id=...` showing both new orders.
- Verified directly against Postgres (not just the UI) via a throwaway `tsx` script:
  - **Both** `Order` rows for this session exist and are `status: "PAID"`, both `buyerId` = ash, both `sellerId` = misty, both stamped with the same `stripePaymentIntentId` (`pi_3UEwr1AVU8YI57Gn2E4ozy5r`) — confirming one payment covered both orders.
  - **Both** `Listing` rows transferred: `ownerId` = ash, `forSale: false`, `price: null`, reservation fields cleared, for both listing ids.
  - A `CardTransaction` audit row exists for each order (one per listing), each with the correct `orderId`/`buyerId`/`sellerId`/`amount`.
  - No `Offer` rows existed on either listing (fresh unreserved listings), so the "archive open offers" step had nothing to archive in this run — logic already exercised and covered by Task 7's offer tests.
  - Misty received **two separate** `card_sold` notifications, one per listing (`listingId` = Starmie GX / Gyarados VMAX respectively, each with its own correct `orderId`), proving `handleCartSessionCompleted`'s per-order loop in `src/app/api/stripe/webhook/route.ts` processes N>1 orders correctly rather than silently dropping all but the first.
  - Ash's cart no longer contains either purchased listing afterward (only an unrelated item belonging to a different, concurrently-running QA task remained — see note below).
  - Neither listing can appear in marketplace browse/search: `src/app/api/cards/route.ts` filters on `forSale === true` from the query string, and both listings are now `forSale: false`.

This confirms the multi-order webhook path (`handleCartSessionCompleted` in `src/app/api/stripe/webhook/route.ts`) already works correctly for N=2 items in one Stripe session — no fix was needed here.

### Note on shared test environment (not an app bug)

This QA sweep runs several tasks in parallel against the **same** shared dev server, shared Postgres DB, and — since Task 5 also uses `ash` as buyer — the same `Cart` row. My first attempt (before I noticed this) used marketplace search-and-click-first-result to add "Starmie GX" to the cart, which is ambiguous when multiple sellers list a card with the same name: it picked up an **admin-owned** "Starmie GX" listing instead of misty's, alongside a real misty-owned Gyarados VMAX, in a 3-item Stripe session that also completed successfully (all 3 `PAID`, all 3 transferred) — but it didn't strictly match the assigned buyer/seller fixture. I left that transaction as-is (it's a fully valid, correctly-processed sale — just not the precise fixture pair) and re-ran the test a second time addressing listings **directly by listing id** (queried from Postgres for misty-owned, unreserved, unambiguous rows) to get a clean, unambiguous 2-item/single-seller verification, which is what's reported above. No source code change was needed for this — it was purely a fixture-selection issue in the test script, not a bug in the app.

Separately, ash's cart also held one item ("Psyduck", `bf88eaad-deb8-41ec-9491-b5cad146e94c`) belonging to Task 5's concurrently-running QA script (buyer = ash there too). I did not touch it directly other than deselecting it immediately before my own checkout POST (so my Stripe charge covered only my two listings) and restoring its `selected: true` flag immediately after, so as not to disrupt Task 5's in-progress flow. This worked cleanly and is visible in the DB verification above (that item remained in ash's cart, untouched, after my checkout completed).

## Found & Fixed

No source code bugs were found in the multi-item checkout path itself — `handleCartSessionCompleted`'s loop-per-order-inside-one-transaction design (with its idempotency check, ownership transfer guard, offer archiving, and cart cleanup) worked exactly as documented on the first clean attempt.

One transient issue was observed but is **not** being treated as an app bug (see reasoning below): during my *first* (contaminated-fixture) checkout attempt, the browser hit a client-side crash on `/checkout/success` — `TypeError: Cannot read properties of null (reading 'useContext')` inside Next's `PathnameContext`, surfaced as a 500 dev-overlay error — right after Stripe redirected back. At the time, system load was extremely high (`uptime` load average ~11.7, ~26 concurrent headless Chromium processes from the ~10 other QA tasks running in parallel tonight, each hammering the same single dev server). I re-tested the exact same `/checkout/success?session_id=...` URL directly via `curl` once load had settled (~3.0) and it cleanly 307-redirected to `/purchases?success=1&session_id=...` every time. My second, clean checkout run also redirected through `/checkout/success` → `/purchases` without incident. Given it reproduced zero times out of two attempts under any load below extreme contention, and the app's own transactional logic (the part that actually matters — payment capture, ownership transfer, notifications) completed correctly regardless of this page-render hiccup, I concluded this is Next.js dev-mode/webpack HMR contention from ~10 concurrent QA agents sharing one dev server, not a deterministic defect in `src/app/checkout/success/page.tsx`. No fix was applied — per the plan's own guidance, this isn't grounds for a speculative fix for something that (so far) can't be reproduced outside extreme concurrent load.

No files were changed for this task. `npx tsc --noEmit` / `npx vitest run` were therefore not required (no `src/lib` or `src/app/api` files were touched), but I ran `npx tsc --noEmit` anyway as a sanity check since I read through `src/app/api/stripe/webhook/route.ts` and `src/app/api/checkout/cart/route.ts` closely enough to consider a change — it passed clean with no errors.
